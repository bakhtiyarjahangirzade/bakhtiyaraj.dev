## Required product

An authenticated owner panel reachable from Luna for authorized editors. Ordinary readers get the normal shop/library; direct attempts to open editor routes or APIs without authorization must fail safely. The panel must be useful on mobile and desktop and match Luna's established design.

1. **Import real files:** PDF, CBZ/ZIP containing ordered images, and individual/multiple JPG/JPEG, PNG and WebP pages. Provide a file picker and drag/drop on desktop; normal file picker on phone. Explain exact supported formats, concrete size/page limits and validation failures before upload. Do not claim CBR/RAR/EPUB support unless genuinely implemented and tested; unsupported files receive clear feedback.
2. **Prepare readable pages:** Render PDF pages to actual images for the current animated reader, not a raw embedded PDF that loses the page-turn experience. Preserve correct order, aspect ratio and legible text. For CBZ/ZIP accept only validated raster images, natural-sort filenames, let the editor reorder, and reject unsafe entries, nested archives, traversal paths and decompression bombs. A renamed HTML/SVG/executable is not an image. Validate actual file signatures and decoded dimensions, not just extensions. Password-protected or malformed PDFs need a useful error. Bound total decoded pixels, pages, memory and expanded archive size.
3. **Import progress and recovery:** Separate upload/conversion progress, pending/failed/ready states, cancellation and retry. Avoid freezing the page or loading an entire large PDF at full resolution simultaneously. Show page thumbnails and allow manual reordering, removing a page and selecting/replacing a cover. Keep draft metadata through retry. Do not leave an apparently published record after a failed import. Repeat/retry must not duplicate comics or assets.
4. **Metadata:** title, slug, creator, synopsis, language, genres, cover, ordered page manifest, credits/rights statement, free versus paid-inquiry status, illustrative/sample flag where applicable, AZN price for owner paid titles, preview-page count and draft/published/unpublished state. Own real works must not inherit the Pepper&Carrot sample disclaimer or attribution. Preserve the existing licensed starter collection and its correct credits.
5. **Preview and publication:** Preview the prepared draft in the exact Luna reader (desktop/mobile) before publishing. Draft -> published should become discoverable in the actual storefront with working title/deep links, library and resume, without code edits or a redeploy per title. Support editing metadata and unpublishing. Use a reversible unpublish/archive action for removal; do not make permanent deletion the default. Replacing content must keep the previously published version intact until the replacement is ready. Stable IDs and progress normalization prevent broken saved libraries when metadata changes.
6. **No payment scope expansion:** Existing Luna has no checkout or paid entitlements. Paid owner comics may offer preview + correctly labeled purchase inquiry to the existing WhatsApp destination. Do not pretend a purchase succeeded, take payment, grant access based on client state or build an unrequested payment integration. A normal visitor must never be able to fetch the non-preview pages or original file of a paid/unpublished title merely by guessing storage paths or changing a query.

## Architecture and security requirements

- Use durable database records and object storage, with the shared Supabase project and server-owned editorial authorization. The local canonical catalogue can remain a seed/fallback, but published uploads need a real maintained data source; avoid two competing definitions of the same title.
- Original PDFs/archives and all unpublished or restricted pages live in private storage. Define explicit table RLS and storage policies for editors, public free/preview reads and ordinary authenticated readers. Do not make a bucket public just to make previews work. Do not leak restricted pages by returning full manifests or signing URLs indiscriminately. Short-lived signed access, when used, must be refreshable for long reading sessions.
- Check permissions on every mutation and signing/import/publication endpoint; hiding panel navigation is insufficient. Anonymous Supabase sessions are not editors. A normal user must not grant themselves a role or write another editor's records. Use verified JWT identity on server routes; no secret/service-role key in browser bundles, URLs, logs, repo or screenshots.
- Provide explicit migrations for new tables/buckets/policies, preserving all existing Luna data. Include a carefully scoped owner-role assignment procedure using the privately provided identity, and a useful nonprivileged state until authorized setup is complete. Do not auto-assign a broader project/admin role. If cloud access cannot apply backend setup, deliver exact migrations/configuration for release review and clearly report the gap instead of faking a working service.
- Respect Vercel request/body/runtime limits: use appropriately bounded direct authenticated/resumable storage uploads instead of sending a large PDF through a tiny function body limit. Choose a realistic browser-worker or server import pipeline. Self-host and pin PDF/archive processing libraries and workers from maintained official packages; inspect current primary documentation. Process sequentially/bounded concurrency. Handle large files gracefully within the actual target environment, not only a tiny fixture.
- The current CSP is self-only for media/assets and already allows the Supabase project for connections. Add only precisely scoped necessary Luna directives (storage images/workers/etc.) if needed, keeping the rest of the site's protections intact. No global unsafe-inline/unsafe-eval wildcard workaround. Preserve route refresh/deep links and offline/read errors.
- Use accessible forms, keyboard alternatives for reordering, visible focus, correct dialog focus return, reduced motion, and honest upload/error feedback. Keep page zoom/swipes and mobile reader behavior working for imported content.
